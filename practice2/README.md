# Конфигурационное управление. Практическая работа № 2

Вариант 7, ИКБО-12-25. Python 3.10+, только стандартная библиотека.

## Назначение

Инструмент читает APKINDEX.tar.gz Alpine Linux напрямую, строит граф
зависимостей рекурсивным BFS, вычисляет порядок загрузки и сохраняет
Mermaid и SVG. Менеджеры пакетов и библиотеки получения зависимостей
в реализации не используются. SVG рисуется собственным рендерером по
тому же графу, из которого сформирован Mermaid; Mermaid CLI не требуется.

## Запуск и проверка

Сборка и установка библиотек не требуются. Из каталога проекта:

```sh
sh run.sh examples/a.csv --stage 1
sh run.sh examples/zlib.csv --stage 2
sh run.sh examples/a.csv --stage 3
sh run.sh examples/a.csv --stage 4
sh run.sh examples/a.csv --stage 5
make test
make demo
```

Без `--stage` выполняется этап 5. На Windows вместо run.sh:
`python -m apkgraph examples/a.csv`, предварительно установив PYTHONPATH=src.
Код возврата 0 означает успех, 2 — ошибку с диагностикой в stderr.
Ошибки доступа к выходному файлу также возвращают 2.

## Конфигурация CSV

Первая строка строго `key,value`. Затем ровно шесть уникальных ключей.
Относительные пути вычисляются от каталога CSV, а не текущего каталога.

| Ключ | Значение |
| --- | --- |
| package | Имя корневого пакета |
| repository | HTTP(S) URL каталога или APKINDEX.tar.gz; в тестовом режиме путь JSON |
| test_mode | Строго true или false |
| output | Путь к SVG; рядом создается файл с расширением .mmd |
| max_depth | Целое 0..200; корень находится на глубине 0 |
| filter | Исключаемая подстрока с учетом регистра; пусто — без фильтра |

Ограничение 200 предотвращает переполнение стека рекурсивного BFS.
На границе глубины узлы показаны, но их исходящие зависимости не читаются.
Фильтр исключает узел и дальнейший обход через него. Если он исключает
корень, конфигурация отклоняется. Пустые, неизвестные и повторные ключи,
неверный URL, отсутствующий тестовый файл и неверные типы диагностируются.

Тестовый репозиторий — JSON вида `{"A":["B"],"B":[]}`.
Имена состоят из заглавных латинских букв; все ссылки должны существовать.
Примеры: ромб A→B,C→D, отдельный узел E и цикл A→B→C→A.

## Этапы и результаты

1. CSV-конфигурация и проверка параметров. Вывод ключ=значение.
2. Загрузка архива, чтение полей P/V/D/p, прямые зависимости.
3. Рекурсивный BFS по целым уровням. Множество посещенных узлов
   обеспечивает завершение на циклах и сохраняет все обнаруженные ребра.
4. Топологическая сортировка: зависимости раньше потребителей.
   Для A результат D → B → C → A. Для цикла выводится ошибка:
   линейного порядка не существует. При ограничении глубины результат
   относится только к раскрытой части графа.
5. Текст Mermaid и SVG. Примеры для zlib, curl, musl находятся в generated.
   Для их повторного построения нужен интернет:

```sh
sh run.sh examples/zlib.csv
sh run.sh examples/curl.csv
sh run.sh examples/musl.csv
```

При проверке прошли 17 тестов. Реальные графы построены по репозиторию
Alpine v3.22/main/x86_64. Это явно выбранный срез, а не обещание актуальной
версии Alpine. Содержимое публичного индекса со временем меняется.

## Сравнение с apk и границы реализации

Фактическое сравнение со штатным apk в этой среде НЕ выполнено:
apk отсутствует, Docker daemon недоступен. Следующие команды — инструкция
для воспроизведения, а не выдуманный протокол проверки. На Alpine с тем же
репозиторием и архитектурой:

```sh
apk update
apk info --depends zlib
apk dot zlib > zlib.dot
apk add --simulate zlib
```

Аналогично проверить curl и musl. Для изображения штатного графа:
`dot -Tsvg zlib.dot -o zlib-apk.svg` (нужен Graphviz).
Сопоставлять нужно множества узлов и направленных ребер, а не расположение.
Штатный apk dot выводит Graphviz, поэтому визуальный стиль будет отличаться.
Порядок apk add зависит также от уже установленных пакетов и транзакции;
порядок программы описывает зависимости полного анализируемого подграфа.

Это анализатор метаданных одного репозитория, а не полный решатель apk.
Ограничения версий удаляются при выделении имени, но совместимость версий
не проверяется. Поля install_if, приоритет провайдеров, архитектурные
альтернативы и скрипты установки не моделируются. Конфликты !name
не считаются зависимостями. Для виртуального имени выбирается только
единственный провайдер; при неоднозначности программа останавливается.
Например, проверка bash обнаружила три провайдера /bin/sh:
busybox-binsh, dash-binsh и yash-binsh. Произвольный выбор скрывал бы
неопределенность, поэтому этот случай показан диагностикой.
Подпись индекса не проверяется: пакеты не устанавливаются и не исполняются.

## Основные функции

- config.load_config / validate / validate_paths: CSV, типы и пути.
- repository.dependency_name: отделение ограничения версии от имени.
- Repository.resolve / dependencies: поиск пакета/provides и зависимостей.
- parse_index / load_remote / load_test: источники данных.
- graph.build_graph: BFS с рекурсивной обработкой уровней.
- graph.load_order: топологический порядок, обнаружение циклов.
- render.mermaid / svg / save: два представления и запись файлов.
- __main__.execute / main: выбор этапа и диагностика CLI.

## История и сдача

В комплекте есть локальный Git-репозиторий с отдельным Conventional Commit
для каждого из пяти этапов. Автор технических коммитов — Codex, не студент.
Проверка: `git log --oneline --reverse`.
Публичный репозиторий еще нужно создать и загрузить туда эту историю:

```sh
git remote add origin URL_ВАШЕГО_РЕПОЗИТОРИЯ
git push -u origin main
```

Generated-файлы исключены из Git и находятся в комплекте как демонстрация.
Задание также требует очной защиты этапов; этот проект ее не заменяет.
